# Design rationale

The actual design lives in [TEMPLATE.html](./TEMPLATE.html) — a complete, self-contained page (inline CSS, vanilla JS, Google Fonts for IBM Plex Sans/Mono, no Tailwind, no build step) with one placeholder, `__PR_DATA__`, to be replaced with the real JSON object. This file exists to record *why* it looks the way it does, for whoever edits it next — not to restate what the template already does.

## Decisions worth knowing before you change them

- **No "too new to judge" risk tier.** An earlier prototype gave `insufficient-history` files their own risk category (dashed badge, sorted last, no score shown) — rejected, because it hid a real signal: the structural layer (blast radius, complexity, coverage gap, path sensitivity) always produces a genuine score, even on a brand-new file. `src/plan/Plan.ts` in the sbxctl validation run was genuinely medium risk *and* insufficient-history at once; showing a dash instead of "Medium risk" would have thrown away the one signal available. Every file always shows its real risk badge. "Changed before" (edit count / "New in this branch") is plain informational text beside it, with no risk coloring of its own.
- **No dedicated "insufficient history" section.** `pr-risk` still tags files that way internally (surfaced in the chat tally), but the page doesn't call it out as its own block — it's not information a first-time reader needs to act on, and the risk badges already carry the signal that matters.
- **Groups default open only when they have findings** (verdict ≠ green, tracked internally even though the verdict label itself is never shown — see below). A clean group collapses by default so attention lands on what needs it.
- **A file can appear under more than one group.** `pr-risk`'s chunking allows two unrelated hunks in the same file to land in different chunks (see `pr-risk/CHUNKING.md`) — the "Reviewed in" column links to every chunk touching that file, not just the first.
- **A file's general risk and a group's Bugs/Risky-spots counts are deliberately styled differently, to stop a reader from treating the risk badge as a summary of the list next to it.** Early versions used a colored pill badge for both; a file's risk score (blast radius, complexity, test coverage, path sensitivity — describes the file in general) and its line-level findings inside *this* diff (often reassuring, e.g. "flagged, but confirmed tested") are independent signals that don't aggregate into each other, and a reader seeing "Risk: Medium" above two "Minor" findings read it as a contradiction. The fix: the risk score is now plain colored text with a small "ⓘ" info icon (no fill, no border beyond the icon itself) that reveals the four structural reasons on hover; "Bugs" and "Risky spots" stay filled, bordered pills, since those genuinely do summarize what's inside. Visual weight now tracks "is this a summary of what you're about to read" rather than treating every risk-flavored number the same way.
- **The four structural reasons render as a 1-3 segment meter plus the reason text, not prose with the grade folded in.** `pr-risk` reports `{ grade, reason }` as two separate fields per reason (see `pr-risk/RISK-SCORING.md`) specifically so the UI never has to parse a grade back out of a sentence like "high — the central reconciliation engine...".
- **Explanations are hover-revealed, not click-expanded.** File-table rows no longer expand, and the per-line notes list under each diff is gone — the "why" for a risk score, a Bugs/Risky-spots chip, or a single flagged line all live in a popover that appears on hovering the relevant "ⓘ" icon or marker, implemented as plain CSS (`.hov:hover > .hov-pop`) rather than tracked click/open state. This needed one real fix: the two containers these popovers live in (the file table's outer border and a group's nested file-diff box) dropped `overflow:hidden`, since a popover that needs to render just below the last line of a short diff would otherwise get clipped by that box's own edge. Rounded corners that `overflow:hidden` used to produce for free are now set explicitly on each box's first child row instead.
- **Bug and risky-spot markers in the gutter are hover targets themselves**, each showing its own severity + line + reason popover directly — no more numbered list underneath to scroll to. The marker's shape still carries meaning without hovering: a filled dot is a bug (colored by severity), a hollow ring is a risky spot (colored by risk level).
- **A line-level "low" flag is never green.** Every other low-risk badge in the page (file rows, group risk, an empty Bugs/Risky-spots chip) uses the same green as "Looks fine" — but on a code line specifically, green reads as "safe to ignore," while a flag's entire purpose is "look here." A flagged line always gets a neutral grey treatment (`LINE_FLAG_LOW`) regardless of how minor; the absence of any flag is the real "nothing to see here" signal. An empty Bugs/Risky-spots chip *is* allowed to go green, since zero findings for the whole group is a genuine all-clear, not a single downplayed flag.
- **The header leads with the branch name as a title, not a small label in a bar**, followed by one fact line (base, file/group counts, a click-to-expand commit timeline, and the total +/− line count summed from the diff data itself, not restated by any skill). The commit timeline is oldest-first, so it reads like a story arriving at the diff, not a changelog counting down.
- **Every `reason` string is a full sentence** (enforced in `pr-risk/RISK-SCORING.md`), since the reader gets no chance to ask a follow-up question.
- **Code in the diff is syntax-highlighted by a small inline tokenizer, not a library.** It classifies comments, strings, numbers, keywords, capitalized type names, call-position identifiers, and property-position identifiers per line with one regex pass — no CDN dependency, no per-file language detection needed, and nothing to break if a script fails to load. The tradeoff is the same as any line-local highlighter: it occasionally mis-colors a line that's only half of a multi-line string or comment, since a hunk never carries the whole file for context.
