# Design rationale

The actual design lives in [TEMPLATE.html](./TEMPLATE.html) — a complete, self-contained page (inline CSS, vanilla JS, Google Fonts for IBM Plex Sans/Mono, no Tailwind, no build step) with one placeholder, `__PR_DATA__`, to be replaced with the real JSON object. This file exists to record *why* it looks the way it does, for whoever edits it next — not to restate what the template already does.

## Decisions worth knowing before you change them

- **No "too new to judge" risk tier.** An earlier prototype gave `insufficient-history` files their own risk category (dashed badge, sorted last, no score shown) — rejected, because it hid a real signal: the structural layer (blast radius, complexity, coverage gap, path sensitivity) always produces a genuine score, even on a brand-new file. `src/plan/Plan.ts` in the sbxctl validation run was genuinely medium risk *and* insufficient-history at once; showing a dash instead of "Medium risk" would have thrown away the one signal available. Every file always shows its real risk badge. "Changed before" (edit count / "New in this branch") is plain informational text beside it, with no risk coloring of its own.
- **No dedicated "insufficient history" section.** `pr-risk` still tags files that way internally (surfaced in the chat tally), but the page doesn't call it out as its own block — it's not information a first-time reader needs to act on, and the risk badges already carry the signal that matters.
- **Groups default open only when they have findings** (verdict ≠ green). A clean group collapses by default so attention lands on what needs it.
- **A file can appear under more than one group.** `pr-risk`'s chunking allows two unrelated hunks in the same file to land in different chunks (see `pr-risk/CHUNKING.md`) — the "Reviewed in" column links to every chunk touching that file, not just the first.
- **Line-level risk flags render as a margin note**, not an inline badge stapled onto the code line — keeps the actual diff text unbroken and readable; the flag's reason sits in its own column to the right.
- **A line-level "low" flag is never green.** Every other low-risk badge in the page (file rows, group risk) uses the same green as "Looks fine" — but on a code line specifically, green reads as "safe to ignore," while a flag's entire purpose is "look here." A flagged line always gets a neutral grey treatment (`LINE_FLAG_LOW`) regardless of how minor; the absence of any flag is the real "nothing to see here" signal.
- **Group verdict labels carry a "Reviewed," prefix** ("Reviewed, no issues" / "Reviewed, minor issues" / "Reviewed, critical issues") to read as the automated Judge's result, distinct from the group's risk pill next to it — risk is "how much this could hurt if something's wrong," verdict is "did we find something wrong." Both can disagree (a high-risk file reviewed with no issues found is still worth a reviewer's attention, which is why the risk pill stays visible even on a clean verdict).
- **Two risk badges per file, worded differently on purpose**: the file table's badge ("High risk") is the file's risk in general; the same file's badge inside a group's diff view ("Risk: High") is the risk of *this specific change* to it. Same underlying value today, different framing, because they answer different questions as the reader zooms in.
- **Every `reason` string is a full sentence** (enforced in `pr-risk/RISK-SCORING.md`), since the reader gets no chance to ask a follow-up question.
